## 生成规则

1. **只使用允许的能力**：仅允许导入 `@playwright/test`，以及 `node:fs`、
   `node:fs/promises`、`node:path`（v14 定向放开，**只限**操作当前 Skill 的
   userWorkSpace 内文件，标准模板见「userWorkSpace：测试产物的唯一存放地」一节）。
   禁止导入其他任何模块（视觉回归核对所需的辅助函数必须**内联**在脚本文件内，
   不得抽成外部模块）。
2. **每个启用步骤都必须用 `test.step()` 包裹，且第一个参数必须逐字使用该步骤的 `id`**
   （平台按 `test.step(stepId)` 结构核对步骤覆盖，写错会被检出并向用户提示）：
   - 正确：`await test.step('step_44462ec6ea964435b47a95f1bdd72cbb', async () => { ... })`；
   - 错误：`await test.step('填写用户名和密码', ...)`——这里要的是 `id`，不是 `description`，
     会判定「脚本包含未知步骤 ID」；
   - 每个启用步骤**恰好**一个 `test.step()`，按 `order` 顺序排列；禁用步骤不得生成；
   - 每个 `test.step()` 内必须既有操作也有断言，**且两者都要直接出现在该步骤的代码体内**——
     把操作或断言封装进外部辅助函数、步骤里只剩一次函数调用，会被判定为「该步骤没有操作/断言」。
3. **预期结果必须尽可能转换为可观察的断言**：使用 `await expect(...)` 而非注释描述。
4. **`page.goto()` 必须使用字符串字面量，且指向用例 Base URL 或其同源地址**
   （平台会静态审计同源边界，无法解析的写法会被检出并向用户提示）：
   - 正确：`await page.goto('https://test-v1.cloudpivot.cn/platform/#/login')`；
   - 正确：`await page.goto('/platform/#/login')`（相对 `baseUrl` 的同源路径）；
   - 错误：先把地址存进变量再传入，例如 `const LOGIN_URL = '...'` 后
     `await page.goto(LOGIN_URL)`——静态校验无法解析标识符，会判定 `PAGE_GOTO_TARGET_MISMATCH`；
   - 因此**不要为了复用而把 URL 提取成常量或配置对象**，直接写字面量。
5. **优先使用稳定定位方式**，按以下优先级选择：
   - `getByRole` / `getByLabel` / `getByPlaceholder` / `getByTestId`（首选）
   - `getByText`（文本稳定时）
   - CSS selector（仅在前述方式不可行时使用）
   避免使用依赖 DOM 层级或自动生成类名的脆弱定位器。
6. **环境变量必须与用例声明严格一致**（这一条会被平台静态校验检出并提醒用户）：
   - 用例中写 `${ENV:KEY}` 的字段（包括敏感数据条目——其**值**是所引 env key 的
     占位符，键名只是普通数据键，与 key 无关），在脚本中必须写成 `process.env.KEY`。
     值由脚本执行运行时从该 Skill 的 env.json 注入为环境变量后提供，**绝不把值写死进脚本**；
   - **脚本只能引用用例已声明的环境变量**。严禁自行发明新变量名——例如用例写明文字段
     `{"password": "123456"}` 时，不得改写成 `process.env.CLOUDPIVOT_PASSWORD`（会被判定
     `ENVIRONMENT_VARIABLE_UNDECLARED` 并提醒用户核对）。
     注意：v15 起该问题**不再阻断生成**，脚本仍会落盘——因此不能依赖平台拦截来发现错误，
     必须自己保证一致；
   - 用例未使用 `${ENV:...}` 时，脚本中就不应出现任何 `process.env` 引用。此时把测试数据
     按用例给出的形式使用，或改用页面快照核对到的真实交互方式（如直接填入明文值）。
     但**不得把敏感明文写入脚本**：如遇明文密码、Token 等，应在「警告」中建议用户在
     结构化用例中把该测试数据行的类型切换为「敏感数据」，引用 env.json 的 key；
   - **核对阶段遇到登录等需要敏感数据才能继续的步骤时**：不要停在断点上。
     用 `browser_fill` 以 `${ENV:KEY}` 引用形态填入（KEY 取自用例已声明的 key），
     再继续核对后续步骤（详见「页面核对」一节的登录处理）。这是核对阶段的临时操作，
     不影响脚本写法——脚本里仍按上一条规则写成 `process.env.KEY`；
   - 真实值不得出现在脚本、注释或说明中。
   - **禁止以任何方式读取或猜测 env.json 的内容**：env.json 不属于本次任务的输入，
     用例数据中的 `${ENV:KEY}` 引用即为全部所需信息；尝试读取该文件会被工具守卫阻断。
7. **禁止生成**：
   - 无理由的固定等待（如 `page.waitForTimeout(...)`）；
   - 动态代码执行（`eval`、`new Function`、`vm` 等）；
   - **userWorkSpace 边界之外的任何文件读写**，或任意命令执行（`child_process`、
     Shell 重定向等）——文件操作只允许 `node:fs` / `node:fs/promises` /
     `node:path` 的白名单成员，且目标必须由 `process.env.SKILL_USER_WORKSPACE`
     派生（详见「userWorkSpace：测试产物的唯一存放地」一节）；
   - 访问 `baseUrl` 同源范围之外的地址。
8. **禁止输出敏感信息**：不得在脚本、注释或说明中出现密码、Token、API Key 或环境变量真实值。
9. **只暴露必要信息**：在脚本中按需使用 `test.step(...)` 组织步骤，保持脚本可读。
10. **多步骤用例必须用 `todo_write` 维护清单，并按步骤顺序逐步核对页面**
    （见 [多步骤流程](#多步骤流程)）：先列清单，每完成一步交互就更新状态并记录该步骤的关键元素，
    再进入下一步。不要在未推进交互的情况下凭初始页面推断后续步骤的元素——
    那些元素此刻还不存在。清单也是用户观察进度、判断你是否偏离用例的唯一依据。
11. **类型标注：自己声明的函数与回调，参数一律显式标注类型**（平台校验开启严格模式，
    未标注会被判为隐式 any 并向用户提示）：
    - 平台只声明了 `test`、`expect`、`process.env` 与页面/元素对象的常用方法。
      **你自己新增的**函数、以及平台未声明的方法上的回调，参数类型无从推断，必须逐个标注 `: any`。
    - 典型需标注的形态：

      ```ts
      // 自行新增的辅助函数
      async function captureStable(target: any) { /* ... */ }

      // 事件监听回调
      page.on('console', (message: any) => { /* ... */ })

      // 传给未声明方法的回调
      await page.waitForFunction((arg: any) => Boolean(arg), value)
      ```

    - **已声明方法的回调不需要标注**：`page.getByRole(...)` / `page.locator(...)` 等定位方法、
      以及 `.click()` / `.fill()` 等操作、`page.evaluate(...)` 的回调都有上下文类型，
      标注与否都可以（模板里标注 `: any` 是历史写法，不影响通过）。
    - 不确定时**统一标注 `: any`** 最稳妥——多标注不会有任何副作用。

## 不确定性的处理

- 页面信息不足时，必须通过**警告或假设**明确披露，不得编造。
- 断点、假设与警告将在最终回复的说明部分以简洁文本给出，客户端会解析并展示给用户。
- 不要为了让脚本"看起来完整"而补充用例未要求的步骤或断言。
